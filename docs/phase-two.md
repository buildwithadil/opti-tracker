## Database migration and preservation

New file: `migrations/0004_customer_management.sql`. Migrations 0001–0003 are unchanged.

The initial customer foundation already existed with `id`, `full_name`, `deleted_at`, nullable phone, optional fields and child foreign keys. The new migration:
1. Renames those fields to `uuid`, `name`, `archived_at`. SQLite rewrites prescription/purchase foreign keys to the renamed UUID key.
2. Stages existing rows and replaces the customer table inside the migration transaction, using `PRAGMA defer_foreign_keys = ON` rather than disabling foreign keys. It reinserts rows after renaming the replacement table, avoiding stale deferred-FK counters.
3. Preserves identifier values, rowids, timestamps, archived metadata and every legacy optional field. It canonicalizes only structurally accepted mobile formats.
4. Adds required canonical phones, the partial active uniqueness index, listing indexes, an internal integer revision, and a permanent-delete rejection trigger.
5. Aborts/rolls back for unsupported legacy phones or active normalized-phone collisions. It never chooses a duplicate winner, merges customers, discards invalid archived rows, or silently invents a number.

Public core schema:

```sql
uuid             TEXT PRIMARY KEY NOT NULL
name             TEXT NOT NULL
phone            TEXT NOT NULL
normalized_phone TEXT NOT NULL
created_at       TEXT NOT NULL
updated_at       TEXT NOT NULL
archived_at      TEXT NULL
```

`phone` is readable `+91 98765 43210`; `normalized_phone` is `+919876543210`. CHECK constraints enforce the canonical number and agreement with its displayed phone. Dates generated by the Worker/SQL defaults are ISO 8601 UTC. New customers use UUIDv4. Legacy optional columns and administrator references remain for safe forward compatibility but are not exposed by the Phase 2 API. `revision INTEGER NOT NULL DEFAULT 0` is internal and not client-editable.

Indexes:
- `uq_customers_active_normalized_phone` on `normalized_phone WHERE archived_at IS NULL`.
- Retained active customer-number uniqueness.
- Name (NOCASE), canonical phone, email, archive/date/UUID indexes for filtering and stable sorting.

An ignored private SQLite backup and preservation fingerprints were taken before migrating the existing local database. The actual local migration applied **21 commands successfully**; a repeat run reported no pending migrations. Checks confirmed:

## Indian mobile normalization

Central utility: `shared/phone.ts`, used by both backend validation and frontend forms. The older generic phone utility remains unchanged for its existing callers.

Equivalent accepted inputs include:
- `9876543210`
- `+919876543210`
- `919876543210`
- `+91 98765 43210`
- `09876543210`

A national mobile must have ten ASCII digits and begin with 6–9. An optional `0`, `91`, `+91`, or `0091` prefix is accepted. One ASCII space/hyphen can separate the prefix and the two five-digit groups. Spaces at the outside are allowed within the 32-character bound.

Arbitrary punctuation is not stripped. Foreign prefixes, malformed/grouped numbers, extensions, Unicode digits, tabs/control characters, repeated separators and invalid lengths are rejected. Parentheses/dots and nonstandard group sizes are deliberately not accepted. Structure validation does not verify ownership, assignment, or reachability; no SMS/OTP integration is added.

## REST API contracts

All six routes are behind the unchanged administrator authentication boundary. Unsafe requests require exact matching `Origin` and the existing `X-CSRF-Token`. The Worker continues to return safe consistent JSON envelopes and `Cache-Control: no-store`.

| Method and endpoint | Behavior |
|---|---|
| `GET /api/customers` | Bounded, sorted, filtered customer list and pagination |
| `POST /api/customers` | Strict `{name, phone}`; creates and audits atomically; HTTP 201 |
| `GET /api/customers/:uuid` | Customer details, including archived records |
| `PATCH /api/customers/:uuid` | Strict nonempty partial `{name?, phone?}`; validates/normalizes/audits |
| `DELETE /api/customers/:uuid` | Soft archive only; identity/history retained |
| `POST /api/customers/:uuid/restore` | Restores only if no active phone conflict |

Archive/restore require no request body. Repeated requests on an already archived/active record return its current representation without duplicate audit events. Archived customer edits are allowed, so a number conflict can be resolved before restoring; editing does not implicitly restore a record.

Public Customer representation:

```ts
{
  uuid: string,
  name: string,
  phone: string,
  normalized_phone: string,
  created_at: string,
  updated_at: string,
  archived_at: string | null
}
```

No financial statistics, purchase/prescription objects, credentials, internal revisions, optional legacy contact fields or actor metadata appear in this representation.

### Listing query

| Parameter | Valid values/default |
|---|---|
| `search` | Trimmed literal substring, maximum 100 characters; default empty |
| `status` | `active` (default), `archived`, `all` |
| `page` | Integer 1–10,000; default 1 |
| `pageSize` | Integer 1–50; default 20 |
| `sort` | `created_at` (default), `updated_at`, `name`, `phone` |
| `order` | `desc` (default), `asc` |

Malformed encoding, duplicate parameters, unknown fields, unsafe sorting and invalid bounds are rejected. Every SQL value is bound; only allowlisted sort identifiers/direction are interpolated. Name wildcards `%`, `_` and `\` are escaped, not interpreted as user-selected patterns. Complete accepted phone inputs use canonical exact lookup; digit-only partial inputs search canonical phone digits. The list and total count execute in one D1 batch/snapshot. UUID ascending is the deterministic tie-breaker.

Success envelope data is:

```ts
{
  customers: Customer[],
  pagination: { page, pageSize, total, totalPages }
}
```

Empty results report zero records and at least one total page. The API returns an empty page for a valid page beyond the end; the UI returns to the last available bounded page.

### Validation and conflict responses

- `INVALID_INPUT` — 400; strict schemas, invalid UUID/name/mobile/query, with field issues where applicable.
- `CUSTOMER_NOT_FOUND` — 404 for a valid absent UUID.
- `CUSTOMER_PHONE_CONFLICT` — 409 for create/edit/restore active-number collisions; includes a `phone` field issue without exposing raw SQL.
- `CUSTOMER_CHANGED` — 409 when another write wins the server-side revision check; reload and retry.
- Existing 401 auth / 403 origin-CSRF / 413 body-size / 415 media-type / safe 500 envelopes remain unchanged.

## Auditing and concurrency

`worker/services/customers.ts` uses the existing immutable `audit_logs` ledger. Customer creation, update, archive and restore record action, customer identity, authenticated administrator, request ID and appropriate public before/after snapshots. They exclude auth/session/IP information and unneeded legacy address/email/notes fields.

Customer write, conditional audit insertion and response snapshot read are one D1 atomic batch. Updates compare an internal persisted revision read by the service, increment it exactly once, and reject a stale competing write. `changes()` plus revision gates prevent a losing mutation from creating an audit even when the winning writer reaches the same next revision. Unique-index enforcement resolves concurrent duplicate creates/edits/restores. Audit insertion failure rolls the customer write back. Reads before writes are not treated as a transaction.

## Known limitations and remaining risks

- Deployed PBKDF2 CPU compliance with Cloudflare's Free plan remains unmeasured from Phase 1. No authentication weakening, remote benchmark/deploy or paid-plan activation occurred.
- SQLite NOCASE/LIKE gives ASCII case-insensitive name matching, not complete Unicode folding or diacritic-insensitive search. Ordinary Unicode names are stored/displayed intact.
- Substring name/partial-phone search and total counts can scan candidate rows; LIMIT bounds returned records, not all read work. Index/query-plan review and a disposable 10,000-row desktop SQLite check are useful but do not prove deployed D1 latency or quota compliance. Account quotas remain finite and shared.
- Full phone normalization supports only documented Indian mobile formats. Broader international/landline input and number verification are not implemented.
- Migration of another populated database requires legacy-phone conflict review and a backup; intentional failure needs controlled data remediation, not a skipped constraint.
- Nonblocking warnings remain: published Blaze sourcemaps reference absent source files; the combined client chunk exceeds Vite's 500 kB warning threshold. No warning suppression or dependency patch was used.
- Vite's Cloudflare plugin copies private development variables into ignored Worker-side build output for local preview. They are not in `dist/client`, but never share/commit private build artifacts. Production secrets still require approved Worker secret provisioning.
- Only Chromium was run. Safari/Firefox and broader device coverage remain future verification. Existing Phase 1 password recovery and remote backup/restore rehearsal remain release gates.
- Purchases, prescriptions, invoices, payments, tax configuration, metrics, reports and CSV exports remain unimplemented. They were not started in this phase.
